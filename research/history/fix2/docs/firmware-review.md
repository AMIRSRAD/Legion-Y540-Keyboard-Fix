This pass read `44.bin` and `SHFU.ini` as data using Python's standard library. It did not execute the updater, contact hardware, or flash anything. All offsets below are file offsets; address mapping and bank selection remain unverified. The companion `../firmware-review.json` preserves raw bytes and calculations, generated by `../tools/firmware_review.py`.

## USB descriptor findings

The descriptor at `0x5307` is a structurally plausible 18-byte USB device descriptor: `12 01 10 01 00 00 00 40 8d 04 00 c1 44 00 01 02 00 01`. Its fields decode as USB 1.10, endpoint-zero packet size 64, VID `048D`, PID `C100`, device revision `0044`, manufacturer string index 1, product string index 2, **serial string index 0**, and one configuration. The main HWID in the INI agrees with this VID/PID.

The configuration tree at `0x531D` has `wTotalLength=0x22` (34 bytes), exactly covering configuration (9), interface (9), HID (9), and endpoint (7) descriptors through `0x533E`. It declares one interface, configuration value 1, attributes `E0` (self-powered and remote-wakeup bits), and `bMaxPower=0x32` (100 mA). Its interface declares HID class 3, boot subclass 1, keyboard protocol 1, and one endpoint. The HID descriptor declares HID 1.10 and a report descriptor of length `0x00A1` (161 bytes). The interrupt-IN endpoint is `0x81`, maximum packet 64, interval 4. These are embedded declarations, not observed enumeration or keyboard behavior. The report descriptor location and contents still need tracing.

## 8051 architecture hypothesis

| Vector offset | Bytes | Candidate `LJMP` destination | Destination bytes |
|---|---|---|---|
| `0000` | `02 01 00` | `0100` | `78 ff e4 f6 d8 fd 90 00 ...` |
| `0003` | `02 32 00` | `3200` | `32 90 07 66 ...` |
| `000B` | `02 33 00` | `3300` | `c0 e0 c0 f0 c0 83 c0 82 ...` |
| `0013` | `02 34 00` | `3400` | `c0 e0 c0 f0 c0 83 c0 82 ...` |
| `001B` | `02 35 00` | `3500` | `32 7e 0c 7f ...` |
| `0023` | `02 36 00` | `3600` | `32 90 07 63 ...` |
| `002B` | `02 37 00` | `3700` | `32 90 0c 34 ...` |

The vector spacing matches classic 8051 reset/interrupt slots. Under that instruction set, `0x32` is `RETI`, while the sequences at `3300`/`3400` push accumulator, B, DPH, and DPL. At `0100`, `78 ff e4 f6 d8 fd` plausibly clears internal RAM using R0, and the following `MOV DPTR`, `MOVX`, and loop instructions plausibly clear external RAM. `75 81 a0` would set the stack pointer to `A0`. This is stronger static support for an 8051-family disassembly candidate than the leading opcode alone. It is not a verified MCU model, memory map, banking scheme, or complete control-flow analysis. Several interrupt destinations immediately return; their precise hardware interrupt assignments need the chip documentation.

## Checksum hypothesis: a useful match, still unverified

INI settings specify start `0400`, end `D800`, high/low addresses `7FFE`/`7FFF`, `CHECKSUMINVERT=1`, and `CHECKSUMMODE=1`. The stored bytes are `56 22`, interpreted in that declared high/low order as `0x5622`.

For the candidate exclusive-end interval `[0x0400,0xD800)`, the 16-bit byte sum including the stored bytes is `0x549C`. Omitting or zeroing those two bytes gives `0x5424`. Replacing both checksum bytes with `FF` before summing gives **`0x5622`**, equal to the stored high/low value:

```text
(0x549C - 0x56 - 0x22 + 0xFF + 0xFF) mod 65536 = 0x5622
```

This is a candidate additive checksum with checksum slots treated as erased flash. The numerical match is useful but does **not** verify the updater's algorithm. Only one image was tested, and the semantics of `CHECKSUMINVERT`, range endpoints, and checksum modes have not been recovered. The script also checks byte/word sums, complements, and `binascii.crc_hqx` initial values 0/FFFF with four field treatments; the only match in this explicitly bounded set is the FF-filled byte sum. That is not an exhaustive checksum search.

Next evidence needed: trace where the native updater reads these INI keys, establish how it treats the checksum field and inversion flag, then test the candidate against an independently sourced second firmware image or a pure offline checksum routine recovered from the updater. Do not use this match as a basis for modifying or flashing firmware.

## Reproduction

From the project folder, run the read-only script against the original files:

```powershell
python tools/firmware_review.py 'C:/Users/owner/Desktop/Y540-keyboard-firmware-00000044/extracted-IT/44.bin' --ini 'C:/Users/owner/Desktop/Y540-keyboard-firmware-00000044/extracted-IT/SHFU.ini'
```

The script's fixed descriptor offsets are specific to this image and are evidence extraction points, not a general firmware parser. Results on another version need independent offset validation.
